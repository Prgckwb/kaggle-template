# 戦略レビュー

確証バイアス・アンカリング・サンクコスト・過度の一般化を構造的に検出するためのレビュー。
**候補の生成と、失敗履歴による絞り込みを分ける**のが要点
（`docs/ai-agent-guidelines.md`「分析とアイデアの役割分担」）。

## フェーズ 1: 問題の理解（失敗履歴はまだ読まない）

読む: `docs/competition-profile.yaml`（type・metric・deadline・selection・workflow）、
`docs/official/overview.md`・`data.md`、`docs/discussion/`、`docs/insights/past_solutions_*.md`。
データ種別（テーブル / 画像 / NLP / 音声・信号 / 時系列 / マルチモーダル / 最適化 / シミュレーション）を判定する。

## フェーズ 2: 探索マップの生成

データ種別に応じて、トップレベルのカテゴリ（5〜10 個）と代表手法のチェックリストを作る。
コンペ固有のドメイン知識や Discussion の手法を足し、合わない項目は削る。出発点の例:

- **テーブル**: GBDT / NN（MLP・FT-Transformer）/ 線形 / 特徴量エンジニアリング（集約・交互作用・target encoding）/ 外部データ / アンサンブル・スタッキング / 後処理
- **画像**: CNN / ViT 系 / 事前学習の選択（自己教師あり・CLIP）/ データ拡張・TTA / 解像度戦略 / 擬似ラベル / 損失の工夫 / アンサンブル
- **NLP**: encoder 系 / LLM fine-tuning（LoRA）/ 従来手法（TF-IDF+GBDT）/ 前処理・最大長 / 擬似ラベル・外部データ / アンサンブル
- **音声・信号**: スペクトログラム + CNN/ViT / 波形直接 / 事前学習音声モデル / 手作り特徴量 + GBDT / 拡張 / アンサンブル

この段階で、各カテゴリについて**このコンペで有望と考える根拠**（データ特性・評価指標・公開情報）を書く。

## フェーズ 3: 既存実験との照合

`EXP_SUMMARY.md`・各 exp の README・`docs/guardrails.md` を読み、探索マップに印を付ける:
`[x]` 探索済み（exp 名・CV/LB を付記）/ `[~]` 一部のみ / `[ ]` 未着手。
カバレッジ = トップレベルカテゴリの（1.0 / 0.5 / 0）の合計 ÷ カテゴリ数（配下の手法は数えない）。

失敗履歴は**フィルタとしてだけ**使う: guardrails の「やってはいけないこと」に当たる候補は外す。
dead-end の exp があっても、そのカテゴリ全体を「効かない」と結論しない（1 実装の結果にすぎない）。

## フェーズ 4: 分析

1. **改善軌跡と停滞**: best の推移を時系列に並べる（方向は `metric.mode`）。停滞は
   `docs/experiment-methodology.md`「停滞の定義」で判定する（ここで独自に定義しない）。
   `noise.seed_spread` が null なら停滞・棄却を断定せず、seed 違いの run を提案する
2. **時間配分**: `competition.deadline` から残り日数を出す。
   序盤（残り > 60%）は探索、中盤は有望軸の深掘りとアンサンブル素材の多様化、
   終盤（< 20% か 2 週間未満）は全 fold 化・seed 平均・`/kaggle:ensemble`・`docs/submissions.md` による final 選定
3. **判定の健全性**（根拠は `docs/experiment-methodology.md`「循環評価」「効果の帰属」「アンサンブルの型」）:
   - 循環評価: 改善を主張する差の介入が、評価と同じ集合から得た知見で設計されていないか
   - 較正点の統制度: 較正点に採ってよいのは、`run_summary.json` の `lineage.parent` で直接つながり
     `lineage.changed` が 1 個のペアだけ。兄弟 run 同士・2 変数以上の比較は採らない
   - アンサンブルの型（部品の質 / 異種部品の追加 / fold ens）ごとに Δ を並べる（このコンペの実測だけで）
4. **exp の肥大化**: `ls src/exp*/config/run*.yaml` で数え、`workflow.max_runs_per_exp` 超過の exp は
   run yaml の `defaults`（親）をたどって系譜の分岐点を分割候補にする
5. **知識のギャップ**: データ・評価指標・リーク・手法について「確認済み」と「仮定」を分ける

## フェーズ 5: レポート

```
=== 戦略レビュー ===
■ 現在地: best = exp{XXX}/{run}（CV x.xxx / LB x.xxx、policy={cv|lb|hybrid}）、締切まで {N} 日（{序盤|中盤|終盤}）
■ 探索マップ: カバレッジ {X}%（[x] {a} / [~] {b} / [ ] {c}）
■ 改善軌跡: {傾向}。停滞判定: {該当/非該当/判定不可（seed_spread 未測定）}
■ 判定の健全性: 循環評価の疑い {…} / 較正点に採れない比較 {…} / アンサンブル型別 Δ {…}
■ exp の肥大化: {超過 exp と分割候補 / なし}
■ 知識のギャップ: 確認済み {…} / 仮定 {…}
■ 次の一手の候補（根拠つき。採否はユーザーが決める）
  1. {カテゴリ / 施策}: {このコンペで有望と考える根拠}
  2. ...
```

候補は未探索・一部探索のカテゴリを優先し、根拠は問題設定・データ特性・公開情報から書く。
停滞時は「なぜ停滞しているかの仮説」と「EDA で確かめるべき仮定」を添える。

## フェーズ 6: 保存と議論

1. 探索マップを `EXP_SUMMARY.md` の「探索マップ」節に保存・更新する（最終更新日・カバレッジ・チェックリスト・候補）。
   別ファイルは作らない
2. ユーザーと方向を議論し、合意した方向を短くまとめる。採用した候補は EXP_SUMMARY.md の探索バックログに入れ、
   実験の作成は `/kaggle:new-experiment` に委ねる
