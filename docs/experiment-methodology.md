# 実験方法論（コンペ非依存）

> **効果の有無を判定する前・dead-end を宣言する前に読む。** コンペ固有の禁止事項は
> `docs/guardrails.md`、学習コードの規約は `docs/training-conventions.md`。
>
> ここに書かれた**数値はすべて「あるコンペでの実測例」**である。自分のコンペの値は
> `docs/competition-profile.yaml` の `metric.meaningful_delta` と `metric.noise` に記録し、
> 判定にはそちらを使う。

## 効果の帰属

🔴 **複数の変数を同時に変えた比較の Δ を、そのうち 1 つの名前で呼んではいけない。**

**なぜ**: 害は記録の不正確さではなく、**次の実験の選択を誤らせること**である。
「A が効く」と読めば A の延長に計算資源を投じるが、実際に効いていたのが B だった場合、
弱い側を延長しながら強い側は未着手で残る。予算はそこで二重に失われる。

**実測例（あるコンペ）**: 旗艦結果として引用されていた Δ+0.0152 / P(Δ>0)=97.9%
（信頼区間が 0 を跨がない = そのプロジェクト最強の証拠）は「入力解像度を上げた効果」として
記録されていた。同じ土俵（単一 fold）で段に分解すると:

| 段 | 変わったもの | Δ | P(Δ>0) | 変数の数 |
|---|---|---:|---:|---|
| ① 小容量・低解像度 → 中容量・高解像度 | 解像度 + 高解像度事前学習重み + 容量 | +0.0049 | **73.1%**（「弱い」域） | **3** |
| ② 中容量・高解像度 → 大容量・高解像度 | **容量のみ** | **+0.0103** | **91.5%** | **1** |
| ①+② | 上記すべて | +0.0152 | 97.9% | 4 |

**容量が 68% を占め、しかも唯一クリーンに 1 変数で切り出せている側だった。**
解像度側は単独では P=73.1% で、記録した本人が同じ文書に「メトリクスを動かしたとは言い切れない」
と書いていた。それでも下流の意思決定は「解像度が効く」で回っていた。

**チェック手順**:

1. 旗艦結果を引用する前に、**基準 run と対象 run の config を列挙して差分の個数を数える**
   （モデル名 / 入力サイズ / epoch 数 / 実効バッチ / 層数 など）
2. 差分が 2 つ以上なら、**中間 run があるか探して段に分解する**。
   分解できたら Δ が加法整合するか確認する（上の例は 0.0049 + 0.0103 = 0.0152 で整合した）
3. 各段の P を個別に見る。**合計の P が高くても、各段が個別に強いとは限らない**
4. 記録には「この Δ は N 変数の合計」と書く。1 変数の名前で呼ばない

### 分解・加算するときは全段を同じ土俵に揃える

🔴 **単体モデル同士の Δ/P と、アンサンブル同士の Δ/P を混ぜて読んではいけない。**
アンサンブルは平均で滑らかになるぶん、同じ実体の差でも Δ と P の出方が変わる。

**実測例（あるコンペ）**: ある実験の README に **同じ `+0.0049` が 2 箇所に別の P で載っていた**
（偶然 Δ が一致した別の比較）。一方はアンサンブル同士で P=87.4%、他方は単一 fold 同士で P=73.1%。
表に「単体同士 / アンサンブル同士」を明記しないと、次に読む人が必ず取り違える。

## 判定の資格

🔴 **単一 fold・単一 seed の差で「効いた」も「dead-end」も宣言してはいけない。**

**なぜ**: 単一 fold の差には seed 運（初期化・データ順・augmentation の引き）が乗る。
その揺れが `meaningful_delta` より大きいのが普通である。さらに
**「CV Δ と LB Δ の一致」も確定の根拠にならない** — CV と LB は同一モデル個体の 2 測定であり、
seed 運の良い個体は両方が高く出る。

**実測例（あるコンペ）**:

- 同一設定で seed のみ変更した 2 run の単一 fold スコアが 0.9094 vs 0.9005 = **揺れ ≈0.009**。
  `meaningful_delta` 0.005 の **1.8 倍**だった
- 教師信号系統だけを変えた 3 構成を、単一 fold と全 fold の両方で LB 測定したところ、
  **単一 fold の順序が全 fold で完全に消滅した**（0.923 < 0.926 < 0.929 → いずれも 0.933）。
  しかも**単一 fold が良いほど全 fold への写像量が小さい**（+0.007 → +0.004）=
  教科書的な**平均への回帰**で、単一 fold の差が実力差ではなく個体の当たり外れだった直接証拠

**判定の資格（階段）**:

| 差の大きさ | 言えること |
|---|---|
| seed 揺れ未満 | **「改善は検出されなかった」（null 結果）**。「棄却」ではない |
| `meaningful_delta` 前後（教師・損失・正則化・条件付けの多く） | 単一 fold では判定不能。**全 fold か複数 seed まで回す** |
| seed 揺れを大きく超える（あるコンペでは入力解像度の Δ+0.011） | 単一 fold のプローブで方向づけしてよい |

**チェック手順**:

1. コンペ開始後の早い段階で **同一設定・seed 違いを 1 本焼き、seed 揺れを実測する**。
   これが以降すべての判定の分母になる。`docs/competition-profile.yaml` の `metric.noise` に記録する
2. 「確定」「決着」「白黒がついた」と書く前に、**差 / seed 揺れ**を計算して併記する
3. seed 揺れの較正点を得た時点で、**それ以前の dead-end 判定は遡って信頼度を下げる**
   （較正前の棄却は「資格のない棄却」だった可能性がある）

## 対照群の設計

🔴 **「重み 0」「係数 0」は、追加したモジュールのベースラインにならない。**
対照群は**モジュールを構築しない設定**（`enabled=false` 相当）にするか、
**モジュールを持つ点どうしで比較する**。

**なぜ**: 重みを 0 にしても forward は走る。モジュール内に dropout など乱数を引く層があり、
かつそれが本体より**先に** forward で呼ばれると、**グローバル RNG を消費して後続の
乱数マスクが全部ずれる**。ベースラインとの差が「モジュールの効果」ではなくなる。

- 🔴 **理由を「初期化が変わるから」と書かない**。モジュールを `__init__` の最後に構築していれば
  共有パラメータの初期値は**ビット単位で一致する**。誤った理由を書くと「weight=0 の run を
  取れば厳密な 0 点」と誤読され、無駄な run を 1 本焼く
- 🔴 **「ゼロ初期化した線形層は RNG を引かない」は誤り**。線形層の `__init__` は
  `reset_parameters()` で一様乱数を引くので**構築時に消費する**（あとからゼロで上書きしても
  消費は取り消せない）。追加モジュールが無害と言える条件は
  **① forward で RNG を引かない ② 既存モジュールより後に構築される** の 2 つが揃うときだけ
- 🔴 乱数マスクの大きさが入力依存でサンプルごとに変わる場合、
  **「消費回数を数えて seed をずらす」補正も成立しない**
- ✅ モジュールを持つ run どうし（係数違い・経路の有無）は RNG 消費が同じなので**内部比較は汚れない**

**実測例（あるコンペ）**: 補助ヘッドを足した実験で、weight=0 と weight 未設定の
train モード logits 差が **3.607e-01**。一方で共有パラメータ 153 テンソルは初期値ビット一致だった。

**チェック手順**（新しいモジュールを足したら毎回）:

1. forward で RNG を引くものがモジュール内にあるか（dropout 以外も拾う）:
   ```bash
   grep -nE "Dropout|torch\.(rand|randn|randperm|bernoulli)|\.bernoulli_" <モジュールの定義ファイル>
   ```
2. `forward` 内でモジュールの呼び出し行 < 本体（encoder / attention）の呼び出し行 か
3. 両方 yes なら、**係数 0 の run を対照群として設計しない**

### 1 変数差分が壊れる実装上の罠

対照群の設計が正しくても、次の 2 つは**意図しない 2 つ目の変数**を混ぜ込む。

- 🔴 **中間特徴を取り出す API は、最終正規化層を通らないことがある。**
  ライブラリ実装では最終 LayerNorm が分類ヘッドの内部にあることが多く、
  `model(x)`（プーリング + 正規化を通る）と `model.forward_features(x)`（通らない）で
  特徴量の分布が変わる。実測（ある CNN backbone）: `forward_features` は std 0.389 / absmax 14.67、
  プーリング + 正規化を通した側は std 0.678 / absmax 3.15。
  → **「集約機構だけを差し替えた 1 変数差分」にならない**。中間特徴を使うなら正規化を明示的に掛ける
- 🔴 **埋め込み層の既定初期化は N(0,1)。加算する相手を圧倒する。**
  埋め込み層は std ≈ 1.0 で初期化される一方、位置埋め込みの慣習的な初期化は std 0.02（**1/50**）、
  正規化後の特徴量も std 0.4〜0.7 で桁が違う。とくに**上位単位のメタ情報を、その配下の
  全トークンに一律加算する**設計は、配下の競争に対して純粋な同相ノイズになる。
  実測（あるコンペ、正規化後）: 新しく獲得させたい軸方向の変動 0.129 に対し、
  既存軸方向の変動 0.607 = **新軸の識別信号が既存軸の 1/10 から学習が始まる**
  （attention score の std も 0.00143 対 0.01406）

**チェック手順**: 新しい軸のトークン・埋め込みを足したら、**正規化後の
「新軸方向の変動」と「既存軸方向の変動」の比を測る**。1/5 を下回るなら初期化を直してから回す。

## 新しい経路は 0 寄与から始める

✅ **新経路はゼロ初期化した残差ゲートで入れ、step 0 でベースラインとビット単位一致させる。**

**なぜ**: これで**「壊れて下がった」と「効かなかった」を分離できる**。
機構を丸ごと差し替えると、劣化したときに原因が仮説側（その情報は無用だった）か
実装側（初期化・正規化・注入形式が壊れていた）かを切り分けられず、
**dead-end の宣言に資格がなくなる**。

**実測例（あるコンペ）**: この技法を持たずに機構を丸ごと差し替えた 3 実験は、
後に seed 揺れの較正点が出た時点で「棄却されたのは仮説か実装か不明」として
まとめて信頼度を下げ直すことになった。ゼロ初期化ゲートを入れた実験だけが、
「実装は正しく動いており効果がなかった」と言い切れた。

**チェック手順**:

1. 新経路のゲート係数（スカラー or 線形層）をゼロ初期化する
2. **1 step だけ回して baseline と logits がビット一致することを実測する**
   （一致しなければ RNG 消費か別経路が混ざっている → 「対照群の設計」に戻る）
3. ゲート係数を毎 epoch ログする。学習後もほぼ 0 なら「経路が使われなかった」であり、
   劣化があってもそれは新経路の寄与ではない

## 機構が仮説を実行できているか

🔴 **「情報を足した」ことは「機構が動いた」ことではない。**
仮説が要求する経路が実際に動いているかを、**他の入力を固定した 1 変数差分で測る**。

**なぜ**: 代表例は softmax のシフト不変性である。attention の全 key に同じベクトルを足しても
重みは 1 ビットも変わらない。得られるのは「条件ごとの定数バイアス」=
**偽相関を当てはめる自由度だけ**であり、仮説が語っていた「注視が正しい場所へ寄る」は起きない。

**実測例（あるコンペ）**: 他の入力を完全固定して条件埋め込みを切り替えた実測:

| 操作 | attention の最大変化 | logits の最大変化 |
|---|---|---|
| **サンプル単位の定数**埋め込みを反転 | **8.8e-06**（一様値の **0.01%**） | 1.22 |
| **トークン別の値**を回す | 3.6e-04 | 0.26 |

attention への影響は **1/41**。仮説は「条件を教えればクエリが正しい側に寄る」だったが、
**機構が仮説を実行できていなかった**。しかも定数バイアスは条件特異的なターゲットに最も害を出すため、
観測された劣化パターンまで説明がついた。

**チェック手順**（条件付け情報を足すとき毎回）:

1. その情報は**要素（トークン・時刻・行）ごとに異なる値**を取るか。取らないなら attention は動かせない
2. 動かしたいなら次のいずれかにする:
   - **入力そのものを変える**（条件に応じて前処理を変える）← あるコンペで実際に効いたのはこれ
   - **要素別の値として入れる**
   - **query 側に入れる**（クエリを条件付ける）
3. 実装したら**他の入力を固定してその変数だけ切り替え、集約の分布の変化量を測る**。
   一様値の 1% を下回るなら、その経路は事実上死んでいる

⚠ **「効かなかった」を「その情報は無用」と記録しない。** 注入形式が無効だっただけの
可能性がある（あるコンペでは、同じ情報を正しい形式で入れ直した実験が最終的な LB best の供給元になった）。

## collapse は獲得させたい軸で層別する

🔴 **collapse の検出統計は、獲得させたい軸に沿って層別してから取る。**
総量で集約すると、**完全に死んだ経路が健全に見える**。

**なぜ**: 設計上は要素ごとに異なる値を出す経路でも、学習が失敗して定数に潰れれば
「サンプル単位の定数」と等価になり、上のシフト不変性で経路が死ぬ。
**構造的な保証と実行時の保証は別物**である。さらに、

- 🔴 **loss の発散だけを監視しても足りない**。平均値への collapse は発散ではなく
  **プラトー**として現れる（ターゲットの平均を出せば loss は中程度で下がり止まる）
- ✅ 監視するのは **要素間のばらつき比**: `std_over_elements(pred) / std_over_elements(target)`。
  0 に向かうなら経路は死んでいる
- ✅ 併せて**集約分布への寄与**を測る。一様値の 1% を下回るなら、loss が下がっていても
  最終タスクには効いていない

**実測例（あるコンペ、同日に 3 例）**: いずれも「総量では見えず、正しい軸で分解して初めて見えた」。

| 誤った測り方 | 正しい軸 | 隠れ方 |
|---|---|---|
| トークン全体の変動 | **群内 vs 群間** | 群間が支配し、群内の信号 1/10 が見えない |
| サンプル内の全トークンで std | **(サンプル, 条件) ごと** | 条件間オフセットが支配し、**完全な collapse に 0.99 を返す** |
| logits の変化量 | **attention 分布の変化量** | logits は 1.22 動くのに attention は一様値の 0.01% |

**2 行目の機序が最も危険なので残す。** 条件ごとに独立した出力層を持つヘッドが、
**同じスロット index に条件ごとに別の物理量を書く**実装は珍しくない:

```python
out = h.new_zeros(feats.shape[0], self.max_dim)
for c, head in enumerate(self.heads):
    out[cond == c, : o.shape[-1]] = o      # ← 条件別ヘッドが同じスロットへ書く
```

slot 0 はどの条件でも同名だが**意味が条件ごとに違う**ので、
**条件を混ぜた統計は非可換な量を足しており、意味を持たない**。
合成データでの実測（3 要素 × 2 条件、条件間オフセット 10.0、条件内変動 0/1/2）:

| ヘッドの状態 | (サンプル, 条件) 内で測る | 条件混在で測る |
|---|---:|---:|
| 健全（pred = 真値） | 1.0000 | 1.0000 |
| **collapse（条件ごとの定数のみ・条件内変動ゼロ）** | **0.0000** ✅ 検出 | **0.9918** ❌ 健全に見える |

しかもこれが**最もありえる collapse モード**である。条件ごとに独立した層があるので
「条件ごとの定数」は最も学習しやすい退避先であり、それは**条件内変動が死んだ状態** =
そのモジュールで獲得しようとしていたものが無い状態に、ちょうど対応する。

**チェック手順**:

1. そのモジュールは**条件によって同じスロットに別の意味を書いていないか**
   （`grep` ではなく出力層の構成とチャネル定義を読む）
2. 書いているなら、統計は**条件ごとに層別してから**取る
3. プール比（`sum(std_pred)/sum(std_target)`）は個別セルの分母爆発に強いが、
   **一部の軸だけの collapse を隠す**（健全な軸の大きい std が和を支配する）。
   **必ず `per_axis_min` を併記し、プール比が健全でも最小値が 0 付近なら「軸ごとに見る」に落とす**

## 循環評価

🔴 **ある検証セット由来の知見で設計した介入を、その同じ検証セットで採点してはいけない。**

**なぜ**: 介入の対象（どのクラス・どのサブセットを狙うか）をその集合の分析で選んだ場合、
測った gain は**選択バイアスを含んで楽観側に歪む**。重要なのは、
**paired bootstrap はこの歪みを検出できない**ことである。bootstrap は
「同じ n 件の上で差が安定しているか」しか測れず、
**その n 件が介入設計に使われていた事実は入力に入っていない**。

**実測例（あるコンペ）**:

- 教師とラベルの一致率分析で**その検証集合上で**選定した対象に介入 → 同じ集合で
  Δ+0.0096 / P(Δ>0)=99.7%。検証集合上は全構成中最高（0.9155）だったのに、
  **LB では 3 番手**（検証順位 0.9155 > 0.9104 > 0.9097 が LB で完全に逆順）
- 別便では、モデル数・多様性・TTA をすべて揃えて部品だけを差し替えた**統制済み 1 変数差分**で
  **LB は完全同値（寄与 ±0.000）**。同じ差が検証集合では **P(Δ>0)=96.4%** まで出ていた
- 🔴 **較正点は「統制された 1 変数差分」からのみ採る**。交絡を 2 つ含む比較
  （モデル数と多様性が同時に違う）から「この P 値は逆方向に出る」という較正点を作ったが、
  統制した便では**「差なし」が正解**だった。**交絡込みの比較から較正点を作ると較正表自体が汚染される**

**チェック手順**:

1. 較正表を引く前に **「その差は、この検証セット由来の知見で設計されたか」を先に問う**。
   Yes なら P 値の大小に関わらず**較正表の適用外**として扱う
2. **測る場所を分ける**: LB プローブ、または独立に切った別集合で評価する
3. 較正表に較正点を追加するときは、**その比較の変数の個数を必ず併記する**。2 以上なら採らない

## プロキシ指標の分解能

🔴 **プロキシ指標の分解能を超えた序列化をしない。とくに「自分が作ったターゲット」での
自己採点で採否・打ち切りを決めてはいけない。**

**なぜ**: 小さい集合ではメトリクスの解像度が測ろうとしている差より大きい。
また、ターゲット自体が自分の作った教師・擬似ラベルである場合、
**「教師に似たモデル」を高く評価するバイアス**があり、独立な指標と順序が逆転しうる。

**実測例（あるコンペ）**:

- n≈60・macro メトリクスの解像度 ±0.04〜0.05 の集合で 0.909 と 0.916 を序列化していた。
  **分解能を超えている**
- 較正表（同一プロキシでの P(Δ>0) → LB での再現）:
  96.2% → 的中 / **96.4%（循環評価あり）→ 完全に不発** / 89.8% → 符号のみ一致・幅は未達 /
  73.1% → 弱い / 56.5% → 不発。**95% 未満の差を順位の根拠にしない**
- 自己採点の検証スコアが 0.9426 < 0.9452 だったため「不発」と判断して学習を打ち切った run が、
  独立に作った検証セットでは **0.9085 vs 0.8982 で逆転**していた（そのプロジェクト最強の証拠になる差）
- 🔴 **擬似ラベルの世代を跨いで「ターゲット再現スコア」を比較してはいけない**。
  pseudo OOF は「与えられたターゲットをどれだけ再現できたか」であり、
  抽出器を変えるとターゲット自体が変わる。v1 で 0.854、v2 で 0.87 でも
  「良くなった」とは言えない（ターゲットが決定的になって当てやすくなっただけと区別できない）。
  → **実験記録には必ずターゲット（ラベルセット）のバージョンを刻む**

**チェック手順**:

1. 打ち切り・採否の判断の**前に**、独立な指標を 1 回回す（ckpt 1 個・数分で済むなら必ず回す）
2. プロキシの P(Δ>0) が 95% 未満の差を順位の根拠にしない
3. 自己採点の検証スコアは **「同一 run 内での epoch 選択」と「同一世代内の粗い進捗確認」に限る**

## 早期打ち切りゲート

🔴 **早期打ち切りゲートを、アーキテクチャ・データ設定を跨いで流用しない。**

**なぜ**: 「ep00 ≥ X / ep02 ≥ Y」型のゲートは、**特定の構成で較正した絶対値**である。
ゼロから学ぶ新規モジュールを含む構成は立ち上がりが遅くて当然で、
そこに旧ゲートを当てると**対策を試す前に打ち切る**ことになる。
これは「効かない」の誤判定を最も安く量産する経路である。

**実測例（あるコンペ）**: `ep00 ≥ 0.75 / ep02 ≥ 0.84` は既存アーキで較正した値だった。
新規モジュールを含む構成に当てて ep03 で打ち切ったが、
その構成の診断メトリクス（注視分布の正規化エントロピー）は 0.9997 → 0.959 と**単調改善していた**。

**チェック手順**:

1. 新しいアーキには**絶対値ゲートを当てない**。「診断メトリクスが単調改善しているか」を見る
2. ゲートを定義するときは**較正した構成名をゲート定義に併記する**。
   併記のないゲートは流用禁止として扱う
3. **コストによる打ち切りはこれとは別枠**で正当である。1 epoch の実測が予算に入らないなら、
   性能の見込みに関わらず打ち切ってよい（→「投入前のコスト実測」）

## アンサンブルの型

🔴 **アンサンブルを 1 つの施策として扱わない。少なくとも 3 つの型があり、効き方が違う。**

**実測例（あるコンペ、8 提出ぶんの実測）**:

| 型 | 実測 | 結論 |
|---|---|---|
| **異種部品の追加・置換**（新 backbone を足す・部品を差し替える・TTA を足す） | 4 例すべて **±0.000** | 🔴 効かない |
| **fold ens**（1 fold → 全 fold） | 毎回 **+0.004〜+0.007** | ✅ 効く |
| **部品の質そのものを上げる** | 単一 fold +0.011 / 全 fold +0.005 | ✅ 効く |

「多様性が足りないから効かない」という説明は、**逃げ道を塞いだ提出で棄却された**:
部品は手持ちで最も帰納バイアスが遠いもの（予測相関 0.916 / 共通誤り率 0.479）、
重みはプロキシ掃引の最良値かつ自然重み 1/(N+1) と一致（= 循環評価も踏んでいない）。
それでも Δ±0.000 だった。
→ **計算資源と提出枠は「部品の質を上げる」型と「fold を増やす」型に集中させる。**

**なぜ単体スコアで採否を決められないか**: 単体スコアは**多様性を過小評価する**。
あるコンペでは、単体プロキシで 0.8896（他の部品の 0.8933 に負けていた）構成が、
4 backbone アンサンブルの構成員として歴代最大の LB 上振れを記録した。
逆に、macro の `ens_gain` が正でも **per-class では全クラスでアンサンブルが単体最良を
超えていなかった**例がある（macro が上がったのは誤りの補完ではなく、
クラスごとの勝ち負けが平均でならされただけ）。

**チェック手順**:

1. 部品の採否は単体スコアではなく **誤りの非相関**（予測相関・共通誤り率）で測る
2. **per-class 表を見て「単体最良を超えたクラスが 1 つ以上あるか」を確認する**。
   ゼロなら補完は起きていない
3. **合否ラインは「単体同士」と「アンサンブル同士」で別に持つ**。
   アンサンブルは平均で滑らかになるぶん相関が高く出る。
   あるコンペの実測較正点（単体同士）: 冗長ペア 0.965/0.639、
   解像度 + 容量差 0.943/0.616、異種アーキ 0.916/0.479 → 合否ラインは相関 < 0.93 / 共通誤り < 0.55。
   同じ集合をアンサンブル同士で測ると、最も離れた 2 構成でも 0.978/0.732 になる
4. `ens_gain` は **「多様性が枯れているかの診断」にのみ使い、採否の予測子にしない**
   （プロキシ +0.0022 に対し LB ±0.000 の実例がある）

## 投入前のコスト実測

🔴 **長時間ジョブは、投入前に 1 epoch の実測コスト（時間・VRAM ピーク・ディスク）を取る。**
見積りだけで投入しない。運用手順は `docs/remote-training-ops.md`。

**なぜ**: **ゲインが出ても払えない構成がある**。しかも律速は直感と外れる:
VRAM ではなくディスクが先に尽きる、定常 VRAM に余裕があっても検証ループのピークで落ちる、など。

**実測例（あるコンペ、同一解像度で 4 種の backbone）**:

| backbone（相対規模） | 分/epoch | 単一 fold（12ep） | 全 fold（5） |
|---|---:|---:|---:|
| A（軽量 Transformer 系） | 19.5 | 3.9h | 19.5h |
| B（中量 CNN 系） | 32 | 6.4h | 32h |
| C（中量 Transformer 系） | 55 | 11h | 55h |
| D（重量 hybrid 系） | **118** | 23.6h | **118h** |

D は ep1 の実測でこれが判明し、**ゲインが出ても払えない**ため打ち切った（正当な打ち切り）。

- 🔴 **解像度を上げる実験は VRAM ではなく前処理キャッシュのディスクが先に律速する。**
  キャッシュは面積比で増える（実測: 低解像度 約 23G → 中 **69G** → 高 約 123G）。
  40GB の VRAM は最高解像度でも 23.4G で余裕だったのに、**400G のディスクに入らなかった**
- 🔴 **VRAM も「定常値」で判断してはいけない。検証ループのピークで OOM する。**
  実測: 定常 19.7〜25.5GB に対し**ピークは 40GB に迫った**。原因は、訓練側だけに入っていた
  入力量の上限が検証側には無く、サンプルあたりの計算量が跳ねたこと。
  → 解像度・入力量を上げるときは、**訓練が収まっても検証で落ちうる**
- 🔴 **backbone を変えたら学習率を据え置いてはいけない。** 事前学習重みの壊れやすさは族ごとに違う。
  実測（差分は lr のみ）: 一律 2e-4 は ep2 に **0.8558 の dip**（= 事前学習重みを壊した痕跡）を作り
  最終 0.9282、backbone 側だけ 5e-5 に下げた側は ep2 **0.8945** / 最終 **0.9378**。
  **「この backbone は使えない」と結論する前に backbone 側の lr を下げて再試行する**
- 🔴 **GPU を余らせたまま長時間回さない。** 小さいモデルを既定設定で流すと GPU 時間を浪費する
  （実測: A100 40GB で VRAM 5.6GB しか使っていなかった → micro-batch と worker 数を上げて 17.4GB）。
  ⚠ **実効バッチ（micro-batch × 勾配累積）は変えない**で micro-batch を上げる
  （そうしないと ablation の比較可能性が壊れる）

**チェック手順**:

1. 1 epoch だけ回して 分/epoch を測り、**単一 fold と全 fold の総時間に換算して予算と比べる**
2. キャッシュサイズと空きディスクを確認する（`du -sh <cache>` と `df -h`）
3. VRAM は**検証ループを 1 回通した後のピーク**を見る（定常値ではない）
4. 開始直後に GPU 使用率・VRAM を実測し、大幅に余っていれば（目安 50% 未満）
   序盤のうちに設定を上げて仕切り直す

## 成果物は照合する

🔴 **判定・提出の前に、実際に使われた成果物をファイル名で照合する。推測しない。**

**なぜ**: best チェックポイントの選択がローカルの glob 依存だと、
**掃除・prune で best が消えてもエラーは出ない**。残った別 epoch が best として扱われ、
`*_best.csv` という名前のファイルに非 best の予測が書かれる。さらに
**どの epoch が生き残るかは prune の実行タイミング依存**なので、
run 間の比較に「成果物品質の偶然差」が混入し、**統制された 1 変数差分が壊れる**。

**実測例（あるコンペの監査）**: 「最新 N 個だけ残す」prune を回していた結果、
複数の run で best が消えていた（例: 遠隔ストレージ側 best は ep16 0.9398 なのに、
ローカルに残っていたのは ep19 0.9390）。predict は無言で後者を使っていた。

**設計と監査**:

- ✅ **prune は best を絶対に削除しない**。resume 用の直近 N 個の外にあっても残す:
  ```bash
  best=$(ls "$d"/*.ckpt | sed -n 's/.*val_\([0-9.]*\)\.ckpt$/\1 &/p' \
         | sort -k1,1gr | head -1 | cut -d' ' -f2-)
  ```
- 🔴 **監査は「遠隔 best ≠ ローカル best」で判定してはいけない。**
  進行中の run は同期が遅れるので、**ローカルのほうが良い ckpt を持っている状態**を
  欠損と誤報する。実損は**遠隔 best がローカル best より厳密に良い**ときだけ
- ⚠ **一括復元オプションは全実験に効く。** 特定の run だけ復元したいなら対象を絞る
  （あるコンペでは意図せず 7 ファイル ≈ 2.9GB を落とした）
- ✅ **配布物（提出に使うデータセット）の実体はファイル名で照合できる**:
  ```bash
  uv run kaggle datasets files {owner}/{dataset-slug}
  # → 全 fold のファイル名に best の epoch とスコアが入っていれば、提出物は正しい
  ```
  **ローカルの mtime やアップロード用ディレクトリの残骸から提出内容を推測しない**
  （残骸は掃除されて消えるが、配布物側のファイル名は残る）

**チェック手順**:

1. best 選択関数の入力が **glob なのか、学習時に記録した値なのか**を確認する
2. prune スクリプトに best 保護があるか確認する（無ければ入れる）
3. 提出・判定の前に配布物のファイル名を一覧し、**選んだはずの ckpt と一致するか照合する**
