# 戦略レビュー: 実験ポートフォリオの俯瞰分析

このスキルは AI エージェントに「一歩引いて全体を見る」ことを強制する。
個々の実験に没頭する前に、探索空間全体を俯瞰し、認知バイアスを検出する。

## 背景: なぜこのスキルが必要か

AI エージェントは以下の認知バイアスに陥りやすい:
- **確証バイアス**: うまくいったアプローチの延長線上でしか考えない
- **アンカリング**: 最初に試した手法に引きずられる
- **サンクコスト**: 時間を投じたアプローチを諦められない
- **過度の一般化**: 少数の実験結果から「この手法は効かない」と結論づける

このスキルはこれらのバイアスを構造的に検出・是正する。

## フェーズ 1: 現状の収集

1. **実験データの収集**
   - `EXP_SUMMARY.md` を Read し、Experiments テーブルと Experiment Tree を把握
   - `src/exp*/README.md` を Glob で検索し、各実験の目的・仮説・結果・考察を Read
   - `src/exp*/config/run*.yaml` を確認し、小実験の数と範囲を把握

2. **蓄積された知見の収集**
   - `docs/insights/` 配下の全ファイルを Read
   - 各知見から「実装上の知見」と「結論・判断」を分離して整理

3. **コンペ情報の収集**
   - `docs/competition-profile.yaml` を Read して `competition.type`・`metric`・`selection.policy` を確認（SSOT）
   - `docs/official/overview.md` を Read してタスクの詳細・評価指標・制約を確認
   - `docs/official/data.md` を Read してデータの特性を確認
   - `docs/guardrails.md` を Read して「やってはいけないこと」を確認
   - `docs/discussion/` があれば最新の議論を確認

## フェーズ 2: 分析（内部処理、以下の全項目を必ず実施）

### 2-1. アプローチファミリーの分類

すべての実験を以下のようなアプローチファミリーに分類する（コンペの種類に応じて適切なカテゴリを使う）:

**テーブルデータの場合:**
- 勾配ブースティング（LightGBM, XGBoost, CatBoost）
- ニューラルネット（MLP, TabNet, FT-Transformer）
- 線形モデル（Ridge, Lasso, ElasticNet）
- 特徴量エンジニアリング重視
- アンサンブル・スタッキング
- その他

**画像データの場合:**
- CNN（ResNet, EfficientNet, ConvNeXt 等）
- Vision Transformer（ViT, DeiT, Swin 等）
- 事前学習モデル活用（CLIP, DINO 等）
- データ拡張戦略
- アンサンブル
- セグメンテーション / 検出ベース
- その他

**NLP の場合:**
- Transformer 系（BERT, RoBERTa, DeBERTa 等）
- 大規模言語モデル（LLM fine-tuning, prompt engineering）
- 従来手法（TF-IDF, Word2Vec 等）
- マルチモーダル
- アンサンブル
- その他

**音声/信号の場合:**
- スペクトログラム + CNN/ViT
- 波形直接処理（1D-CNN, WaveNet）
- 事前学習モデル（wav2vec, HuBERT, BEATs 等）
- 手作り特徴量（MFCC 等）+ 勾配ブースティング
- アンサンブル
- その他

実際のコンペの種類に合わせて適切なカテゴリを構成する。

### 2-2. 改善軌跡の分析

まず `docs/competition-profile.yaml` を Read し、`metric.mode`（max/min）と `meaningful_delta` を確認する。

- 全実験の CV/LB スコアを時系列に並べ、改善トレンドを分析（`min` 指標では減少が改善）
- 直近 3 実験の CV 改善量（mode を考慮した符号）を計算
- **停滞検出**: 直近 3 実験の CV 改善量が合計で基準値未満の場合、「停滞状態」としてフラグを立てる。基準値の優先順位:
  1. `meaningful_delta`（設定済みの場合）
  2. 未設定なら best 実験の `logs/{run_name}/run_summary.json` の `folds` から fold 間標準偏差 `std` を計算し、`ノイズフロア = std / sqrt(n_folds)` を使う（これ未満の改善は fold 間ノイズと区別できない）
  3. それも取れなければ、そのコンペのスコアスケールで有意といえる幅をユーザーに確認する

### 2-2b. 時間軸の分析

`docs/competition-profile.yaml` の `competition.deadline` を確認し、残り日数を計算する（未設定なら `docs/official/overview.md` のタイムラインを参照。それでも不明ならスキップ）。

残り時間はフェーズ 3 の戦略提案に反映する:

- **序盤（残り > 60%）**: 探索重視。未探索アプローチファミリーへの投資を推奨
- **中盤（残り 20〜60%）**: 有望アプローチの深掘りと、アンサンブル素材の多様性確保を並行
- **終盤（残り < 20% または 2 週間未満）**: 新規大実験より、既存 best の安定化（seed 平均・全 fold 学習）、アンサンブル（`/kaggle:ensemble`）、`docs/submissions.md` に基づく final submission 選定を優先

### 2-3. 未探索領域の特定（最重要）

- アプローチファミリーのうち、まだ試していないカテゴリを列挙
- **必ず 2 つ以上の未探索アプローチファミリーを提示すること**（見つからない場合は、既存カテゴリの組み合わせや、そのコンペ特有の斬新なアプローチを考案する）

### 2-4. 知識のギャップ分析

以下を「わかっていること」と「仮定にすぎないこと」に厳密に分離する:

- **データについて**: 分布、外れ値、欠損パターン、クラス不均衡、時系列性
- **評価指標について**: 最適化の方向性、閾値の影響、部分スコアの重み
- **リーク・情報源について**: テストデータの分布、train/test のドメインシフト
- **有効な手法について**: 実験で確認済みか、Discussion 情報か、推測か

## フェーズ 3: レポートの提示

以下の構造でユーザーに報告する。冗長にならず、判断に必要な情報を簡潔に示す。

### レポート構造

```
=== 戦略レビュー ===

■ 実験サマリー（{N}件の大実験、{M}件の小実験）

| アプローチファミリー | 実験数 | Best CV | Best LB | 状態 |
|---------------------|--------|---------|---------|------|
| ...                 | ...    | ...     | ...     | ...  |

■ 改善軌跡
- 現在の Best: exp{XXX} (CV: x.xxx, LB: x.xxx)（判定: selection.policy = {cv|lb|hybrid}）
- 直近3実験の改善: {改善量}（{評価}。基準値 {meaningful_delta or ノイズフロア}）
- [停滞検出時] ⚠ 直近3実験の改善が基準値未満です。根本的に異なるアプローチを検討してください。

■ 時間軸
- 締切: {deadline}（残り {N} 日、進行度 {X}%）→ フェーズ: {序盤|中盤|終盤}

■ 探索カバレッジ
- 探索済み: {N}/{M} カテゴリ（{X}%）
- 未探索のアプローチファミリー:
  1. {カテゴリ名}: {このコンペで有望と考える理由}
  2. {カテゴリ名}: {このコンペで有望と考える理由}
  [必ず2つ以上]

■ 知識のギャップ
- わかっていること:
  - ...
- 仮定にすぎないこと（検証が必要）:
  - ...

■ 戦略提案
{分析に基づく具体的な次の一手の提案。停滞時は特にラディカルな方向転換を提案する。}
```

### 停滞時の特別対応

停滞検出（2-2 の基準）に該当した場合、通常の提案に加えて以下を必ず含める:

- **なぜ停滞しているかの仮説**（同じアプローチの微調整に留まっている、データの特性を見落としている、等）
- **ラディカルな方向転換の提案**: 現在のアプローチとは根本的に異なる手法を少なくとも 1 つ具体的に提案する
- **検証すべきデータの仮定**: まだ検証していないデータの性質を挙げ、EDA で確認することを提案する

## フェーズ 4: 方向性の議論

レポートを提示した後、ユーザーと議論する:

- 「この分析に基づいて、次はどの方向に進みたいですか？」
- ユーザーが選んだ方向について、具体的な実験の方向性をさらに議論する
- ただし、実験の作成自体は `kaggle:new-experiment` に委ねる

最終的に合意した戦略の方向性を簡潔にまとめて終了する。
